# 全量化 AI 工作流搭建说明

本文档是一套通用的“从项目设计到执行闭环”的 AI 协作工作流。它适用于代码项目、设计项目、数据项目、自动化项目、研究项目、内容项目、运维项目和团队协作项目。

本文档不绑定任何具体 AI 工具。你可以把它用于代码代理、聊天式 AI、IDE 助手、本地自动化助手、MCP 客户端、浏览器代理或团队内部 AI 工作台。

核心目标：

```text
需求明确 -> 边界清楚 -> 执行可控 -> 结果可验 -> 风险可回滚 -> 证据可追踪 -> 后续可交接
```

---

## 1. 工作流要解决什么

一套完善的 AI 工作流应该解决以下问题：

1. AI 接手任务时知道先读什么，而不是凭空猜。
2. AI 知道项目边界、权限边界、密钥边界、提交边界和生成物边界。
3. AI 能把用户请求转换成任务等级、验收标准和风险等级。
4. AI 能区分“只读分析”“规划”“执行”“验证”“收尾”。
5. AI 不只生成方案，也能在授权范围内完成实现、验证和同步。
6. AI 会把长期结论写入项目文档、证据或任务记录，而不是只留在聊天里。
7. 下次会话或另一个人能从文档和证据继续，不需要重复解释上下文。
8. 高风险操作有人工确认、回滚方案、审计记录和失败处理。

---

## 2. 通用分层

建议把 AI 工作流分成 5 层。

| 层级 | 示例名称 | 作用 | 是否项目专属 |
|---|---|---|---|
| 全局使用原则 | 全局 AI 偏好、全局安全规则、个人协作风格 | 定义跨项目通用习惯，例如是否先计划、是否偏好简洁回复、是否禁止自动提交 | 否 |
| 全局能力包 | skill、playbook、workflow card、tool guide | 提供某类任务的通用流程、脚本、参考资料或工具使用方法 | 通常否 |
| 工具服务器配置 | MCP server、插件、CLI、浏览器自动化、知识库连接 | 让 AI 能访问文件、命令行、浏览器、数据库、文档库或外部系统 | 否或半专属 |
| 项目入口文档 | `AGENTS.md`、`AI_GUIDE.md`、`.ai/guide.md` 等 | 告诉 AI 当前项目如何工作，优先级高于全局能力包 | 是 |
| 项目规则与证据 | 项目规则、设计文档、脚本、测试、验收记录、运行手册 | 保存项目真实状态、验证入口、风险和交接信息 | 是 |

推荐优先级：

```text
用户最新请求
> 当前项目 Agent 入口文档
> 项目规则、README、文档、运行手册、验收结果
> 全局能力包或 skill
> 全局个人偏好
```

这个顺序很重要。全局 skill 或通用 playbook 只能提供方法，不能覆盖当前项目真实规则。

## 3. 推荐项目结构

不同项目结构可以不同，但建议至少有这些入口。

```text
ProjectRoot/
├─ AGENTS.md 或 AI_GUIDE.md       # AI 项目入口文档
├─ project_rules.md               # 项目工程规则，可选但推荐
├─ README.md                       # 面向人类的项目说明
├─ docs/                           # 设计、需求、验收、证据、运行手册
├─ scripts/                        # 构建、启动、测试、验收、同步检查脚本
├─ tests/                          # 自动化测试
├─ src/ 或 app/                    # 项目源码或主要产物
├─ config/                         # 配置模板，不放真实密钥
└─ artifacts/ 或 build/            # 生成物、日志、验收产物，通常不提交
```

项目不写代码也可以使用类似结构：

```text
ProjectRoot/
├─ AI_GUIDE.md
├─ README.md
├─ docs/
│  ├─ 项目目标.md
│  ├─ 决策记录.md
│  ├─ 验收记录.md
│  └─ 风险清单.md
├─ assets/
├─ outputs/
└─ scripts/
```

核心不是目录名，而是职责清楚。

## 4. Agent 入口文档

Agent 入口文档可以叫：

- `AGENTS.md`
- `AI_GUIDE.md`
- `ASSISTANT.md`
- `.ai/guide.md`
- `.github/copilot-instructions.md`
- 团队约定的其他名称

它的作用是让 AI 进入项目后立刻知道：

1. 优先读什么。
2. 哪些文件可以改，哪些不能碰。
3. 哪些信息不能提交、不能公开、不能写进文档。
4. 不同任务等级该跑什么验证。
5. 哪些行为需要用户确认。
6. 收尾时如何同步文档、证据和交接信息。

### 4.1 推荐结构

```text
# Project AI Workflow

## Priority
## Project Map
## Safety Boundaries
## Task Levels
## Roles
## Standard Workflow
## Verification Matrix
## Documentation And Evidence Rules
## Tool And Permission Rules
## Git Or Publishing Rules
## Handoff Template
## Common Pitfalls
```

### 4.2 与项目规则文档的区别

| 文档 | 面向对象 | 内容重点 |
|---|---|---|
| Agent 入口文档 | AI 助手和自动化代理 | 怎么接手、怎么分级、怎么查、怎么验证、怎么收尾 |
| 项目规则文档 | 开发者、团队和 AI | 架构边界、编码规范、目录规则、文档规则、安全规则、提交规则 |
| README | 项目用户和协作者 | 项目介绍、安装、运行、基本使用 |
| docs | 长期项目知识 | 设计、需求、验收、运行手册、证据、风险、交接 |

Agent 入口文档应该短而实用。项目规则文档可以更详细。

## 5. 项目规则文档

项目规则文档用于固化项目工程纪律。它回答：“这个项目如何保持可维护和安全？”

推荐包含：

```text
## 项目定位与技术基线
## 仓库结构
## 架构分层
## 编码规范
## 注释规范
## 配置与密钥规则
## 数据与隐私规则
## 脚本和自动化规则
## 测试与验收规则
## 文档和证据规则
## Git / 发布 / 交付规则
## 安全和权限规则
## 禁止事项
## 例外处理
```

适合写进项目规则：

- 技术栈和工具链。
- 构建输出约定。
- 源码层级和依赖方向。
- 文件命名、脚本命名、注释风格。
- 用户可见文案或配置模板位置。
- 数据库、协议、接口、模型边界。
- 文档索引和证据落点。
- 密钥、日志、数据库、缓存、生成物、个人素材的处理方式。
- 提交、发布、导出、部署规则。

不适合写进项目规则：

- 真实密钥。
- 真实账号密码。
- 一次性聊天结论。
- 临时 debug 日志。
- 没有长期价值的局部思考。

## 6. 文档体系

全量闭环推荐至少有 5 类文档。

| 类型 | 作用 |
|---|---|
| 总设计 | 项目目标、范围、用户、架构、阶段计划 |
| 模块需求 | 每个模块要实现什么、验收口径是什么 |
| 模块设计 | 分层、接口、数据流、职责边界 |
| 验证证据 | 最新一次可证明状态、命令、结果、产物、残余风险 |
| 工作流索引 | 先读什么、改完同步什么、如何防止文档和脚本漂移 |

轻量项目可以只有：

```text
README.md
AI_GUIDE.md
docs/验收记录.md
```

长期项目建议补：

```text
docs/文档索引.md
docs/任务结束闭环清单.md
docs/验证证据总档案.md
docs/风险清单.md
docs/决策记录.md
```

### 6.1 决策记录

复杂项目建议保留决策记录，记录：

- 做了什么决定。
- 为什么这么做。
- 放弃了什么方案。
- 决策影响哪些模块。
- 何时需要重新评估。

可用格式：

```text
Decision:
Context:
Options:
Chosen:
Reason:
Consequences:
Review Trigger:
```

### 6.2 证据文档

证据文档应表达“最新可证明状态”，不要堆互相矛盾的旧结论。

推荐格式：

```text
Date:
Scope:
Command Or Method:
Result:
Artifacts:
Conclusion:
Residual Risk:
Next Step:
```

如果新证据覆盖旧证据，重写对应章节，使文档表达当前事实。

## 7. 脚本和自动化体系

脚本是工作流可靠性的关键。通用脚本分类：

| 分类 | 作用 |
|---|---|
| build | 构建或生成项目产物 |
| test | 单元测试、集成测试、静态检查 |
| start / stop / status | 启动、停止、状态检查 |
| validate | 专项验证，例如协议、数据、UI、性能、安全 |
| accept | 贴近真实用户路径的验收 |
| check-workflow | 检查文档、脚本、证据、密钥、Git 边界是否同步 |
| backup / restore | 备份和恢复 |
| deploy / rollback | 发布和回滚 |

脚本应满足：

- 名称表达职责。
- 参数可预测。
- 输出能区分 PASS / FAIL / WARN。
- 失败时保留必要诊断信息。
- 产物落到固定目录。
- 新增或改名后更新文档索引。

通用命令示意：

```text
scripts/build
scripts/test
scripts/start
scripts/status
scripts/validate
scripts/check-workflow
scripts/scan-secrets
scripts/backup
scripts/rollback
```

不要把示意命令当作固定要求。按项目技术栈替换。

## 8. 任务等级

建议固定使用 L1-L4。

| 等级 | 名称 | 适用范围 | Definition of Done |
|---|---|---|---|
| L1 | Quick | 小文案、注释、低风险说明、轻微配置提示 | 读直接相关文件，做最小改动，静态或可读性检查通过或说明不适用 |
| L2 | Standard | 普通 bug fix、局部功能、脚本、测试、小重构 | 读相关规则和设计，运行 targeted test，同步必要文档 |
| L3 | Full Closure | 跨模块、用户主流程、协议、持久化、数据处理、外部服务、明确要求闭环 | 真实路径或可信验收通过，证据更新，工作流同步检查通过，残余风险明确 |
| L4 | Release/Risk | 发布、迁移、删除、安全、权限、生产、不可逆操作、敏感数据 | L3 完成，另有回滚、监控、发布后验证、审计记录和人工确认 |

升级规则：

- 小任务触碰真实用户路径，升级。
- 局部改动影响数据或权限，升级。
- 构建通过不能证明真实行为，升级验证。
- 涉及生产、删除、迁移、外部系统写入，必须 L4。

---

## 9. 风险等级和人工确认

除了任务等级，还建议定义风险等级。

| 风险 | 示例 | AI 行为 |
|---|---|---|
| R0 | 只读分析、解释代码、草拟文档 | 可直接执行 |
| R1 | 小范围文件编辑、无外部副作用 | 可执行，收尾说明 |
| R2 | 运行测试、安装开发依赖、生成临时产物 | 执行前确认项目规则，必要时提示 |
| R3 | 修改配置、数据库写入、外部 API 调用、批量重命名 | 需要明确授权和回滚/备份 |
| R4 | 删除、迁移、发布、生产变更、权限变更、推送、财务或安全相关操作 | 必须人工确认，记录审计和回滚方案 |

AI 默认不应自动执行：

- 删除大量文件。
- 覆盖数据库。
- 推送远端。
- 发布生产。
- 修改权限。
- 访问或写入外部系统。
- 安装高权限 hook。
- 暴露或复制密钥。

## 10. 逻辑角色

即使只有一个 AI，也建议按角色思考。

| 角色 | 职责 | 输出 |
|---|---|---|
| PM | 目标、范围、等级、验收标准、风险 | 计划、边界、验收命令 |
| Explorer | 只读调查代码、文档、脚本、证据 | 事实、路径、当前状态 |
| Builder | 最小实现，遵守边界 | 代码、文档、脚本修改 |
| Tester | 运行能证明结果的验证 | 命令、结果、产物 |
| Reporter | 同步文档、证据、风险和交接 | 证据、总结、下一步 |

小任务可以把这些角色合并。大任务建议显式分阶段。团队或多代理场景可以拆分角色，但必须避免多个代理同时写同一文件。

## 11. 标准执行流程

### 11.1 Intake

明确：

- 用户要什么结果？
- 输出物是什么？
- 哪些文件、系统或数据会被影响？
- 是只读、规划还是执行？
- 任务等级和风险等级是什么？
- 需要哪些验收标准？
- 是否需要用户确认？

### 11.2 Explore

读取：

- Agent 入口文档。
- 项目规则。
- README 或文档索引。
- 相关设计、需求、运行手册、验收记录。
- 相关源码、脚本、测试、配置模板。

探索阶段默认只读。

### 11.3 Plan

输出简短计划：

```text
目标:
影响范围:
任务等级:
风险等级:
执行步骤:
验证方式:
需要确认:
```

如果用户要求直接执行且风险低，可以边做边更新计划。高风险任务必须先确认。

### 11.4 Build

原则：

- 做最小 coherent change。
- 遵守项目分层和命名。
- 不做无关重构。
- 不回滚他人或用户的无关改动。
- 不写真实密钥。
- 不把临时日志或私有数据写入长期文档。

### 11.5 Test

验证强度随风险提高：

- L1：静态或可读性检查。
- L2：targeted test。
- L3：真实路径或可信验收。
- L4：L3 + 回滚验证 + 发布后检查 + 人工确认。

### 11.6 Report

收尾说明：

- 改了什么。
- 为什么改。
- 跑了什么验证。
- 结果是什么。
- 哪些没有验证。
- 风险和回滚是什么。
- 是否更新文档和证据。
- 下一步是什么。

## 12. 安全闭环

完整工作流必须包含安全闭环。

### 12.1 数据分级

建议将数据分成：

| 等级 | 示例 | 处理规则 |
|---|---|---|
| Public | 公开 README、开源代码、公开文档 | 可公开引用 |
| Internal | 内部设计、非敏感日志、团队流程 | 不外发，写文档时谨慎 |
| Confidential | 账号、私有地址、客户信息、业务数据 | 不写入公开文档，最小化访问 |
| Secret | 密钥、token、密码、私钥、session | 不展示、不复制、不提交、不长期保存 |
| Regulated | 医疗、金融、未成年人、法律、身份信息等 | 需要额外合规和人工确认 |

### 12.2 密钥处理

规则：

- 使用配置模板，不写真实值。
- 密钥通过环境变量、密钥管理器或受控配置注入。
- 日志和错误输出中脱敏。
- 提交前运行 secret scan。
- 发现密钥泄露时，立即停止传播、轮换密钥、记录影响范围。

### 12.3 权限最小化

- 文件工具只开放必要目录。
- 命令工具只执行必要命令。
- 外部系统默认只读。
- 写入、删除、发布、迁移必须明确授权。
- 自动化工具的权限应可审计。

### 12.4 供应链安全

新增依赖前检查：

- 来源是否可信。
- 许可证是否可接受。
- 维护状态是否正常。
- 是否需要网络或高权限。
- 是否可用已有依赖替代。
- 是否锁定版本。

### 12.5 AI 输出复核

AI 可能生成错误代码、虚构 API、遗漏边界或过度自信结论。高风险场景必须：

- 引用真实文件和命令。
- 使用测试或验收证明。
- 对外部事实查证来源。
- 对安全、法律、金融、医疗、生产发布保留人工确认。

## 13. 回滚和恢复

L3/L4 任务建议有回滚思路，L4 必须有。

回滚清单：

```text
变更前状态:
备份位置:
回滚命令:
验证回滚成功的方法:
不能回滚的部分:
人工确认人:
```

常见恢复动作：

- Git revert 或恢复备份。
- 恢复配置模板。
- 回滚数据库迁移。
- 停止服务或回退版本。
- 清理生成物。
- 撤销外部系统写入。
- 轮换泄露密钥。

---

## 14. 审计和交接

长期项目应保留：

- 谁发起任务。
- AI 做了什么。
- 改了哪些文件。
- 跑了哪些命令。
- 哪些结果通过。
- 哪些风险未覆盖。
- 哪些操作需要人工确认。

交接模板：

```text
Goal:
Current State:
Important Files:
Decisions:
Validation:
Risks:
Rollback:
Next Step:
```

## 15. Skill / 能力包

Skill 是 AI 的可复用能力包，也可以叫 playbook、capability、workflow card 或 tool guide。

适合承载：

- 某类任务的通用流程。
- 工具使用方法。
- 稳定脚本。
- 参考资料。
- 模板资产。
- 验证标准。

不适合承载：

- 某个项目的真实私有路径。
- 某个项目的真实密钥或账号。
- 一次性聊天结论。
- 只有单个项目适用的长期状态。

### 15.1 推荐结构

```text
skill-name/
├─ SKILL.md
├─ scripts/
├─ references/
└─ assets/
```

`SKILL.md` 应包含：

- name。
- description 或触发条件。
- 快速流程。
- 何时读取 references。
- 何时运行 scripts。
- 验证方式。
- 禁止事项。

### 15.2 创建条件

满足任一条件时可创建：

- 同类任务反复出现。
- 每次都需要同一批参考。
- 每次都要写类似脚本。
- 有固定验证流程。
- 需要把团队知识交给 AI 稳定使用。

### 15.3 设计原则

- 保持通用。
- 主文件短。
- 详细资料放 references。
- 确定性操作放 scripts。
- 不包含密钥。
- 不覆盖项目规则。

## 16. MCP 和工具服务器

MCP 或其他工具服务器用于让 AI 调用外部能力，例如：

- 文件读写。
- 命令行。
- 浏览器自动化。
- 文档库。
- 数据库。
- 项目管理系统。
- 错误监控。
- 云服务。

### 16.1 工具配置原则

1. 只开启需要的工具。
2. 权限最小化。
3. 密钥不写进文档。
4. 外部系统默认只读。
5. 写操作需要授权。
6. 工具配置不替代项目规则。
7. 修改工具配置后，用低风险操作验证。

### 16.2 工具说明模板

```text
Tool Name:
Purpose:
Access Level:
Allowed Operations:
Forbidden Operations:
Credential Source:
Validation Method:
Owner:
Review Date:
```

## 17. Prompt Templates

推荐准备通用提示词模板。

### 17.1 继续

```text
请按当前项目 Agent 入口文档和项目规则继续。先读取项目文档、结果文件和已有证据，从已记录的下一步推进；不要让我重复上下文。任务：{{task}}
```

### 17.2 只读

```text
只做只读分析，不改文件，不运行有副作用命令。请读取相关规则、文档、源码、脚本和证据，输出结论、证据路径、风险和可执行下一步。任务：{{task}}
```

### 17.3 计划

```text
先进入规划模式。请给出目标、影响范围、任务等级、风险等级、执行步骤、验证方式、需要我确认的事项。确认前不要改文件。任务：{{task}}
```

### 17.4 标准执行

```text
按标准工作流执行。读取相关规则和文档，做最小实现，运行 targeted test，同步必要文档；如果影响运行时主路径、数据、权限或外部系统，请升级等级并说明原因。任务：{{task}}
```

### 17.5 完整闭环

```text
按完整闭环执行。完成规划、探索、实现、验证、证据同步、风险说明和交接。涉及发布、删除、迁移、生产、权限或敏感数据时，必须先等待人工确认。任务：{{task}}
```

## 18. 全量工作流搭建步骤

### Step 1：建立全局使用原则

写清：

- AI 默认是否先计划。
- 哪些操作禁止自动执行。
- 回复风格偏好。
- 是否允许创建/修改文件。
- 是否允许运行命令。
- 是否允许访问外部系统。

### Step 2：建立项目 Agent 入口文档

写清：

- 项目地图。
- 必读文档。
- 安全边界。
- 任务等级。
- 验证矩阵。
- 收尾规则。
- 人工确认点。

### Step 3：建立项目规则

写清：

- 技术栈。
- 架构边界。
- 编码规范。
- 文档规则。
- 数据和密钥规则。
- Git 和发布规则。

### Step 4：建立文档索引和证据记录

至少保留：

- 文档索引。
- 验收记录。
- 决策记录。
- 风险清单。

### Step 5：建立脚本入口

至少保留：

- 构建或生成。
- 测试或校验。
- 启动或状态检查。
- 工作流同步检查。
- secret scan。

### Step 6：建立安全门禁

至少包含：

- secret scan。
- 生成物忽略。
- 数据分级。
- 高风险确认。
- 回滚方案。
- 审计记录。

### Step 7：建立能力包

为高频、跨项目任务创建 skill 或 playbook。

### Step 8：建立工具服务器说明

为每个工具记录用途、权限、密钥来源和验证方式。

### Step 9：试运行

用 3 类任务试跑：

- L1 小文档改动。
- L2 小功能或 bug fix。
- L3 真实路径验收。

试跑后根据体验调整文档长度、提示词和验证矩阵。

## 19. 完成标准

一套全量工作流算完成，至少满足：

- 有项目 Agent 入口文档。
- 有项目规则或等价说明。
- 有测试或验证入口。
- 有 secret 和生成物边界。
- 有任务等级和风险等级。
- 有文档或证据落点。
- 有高风险人工确认规则。
- 有回滚或恢复思路。
- 有交接模板。
- 有工具权限说明。

成熟工作流还应具备：

- 工作流同步检查。
- secret scan 自动化。
- 证据质量检查。
- 文档链接检查。
- 依赖和供应链检查。
- 运行健康仪表盘。
- 发布和回滚 runbook。

## 20. 常见误区

1. 入口文档太空，不写真实边界和验证入口。
2. 通用 skill 里塞项目私有路径或私有规则。
3. 只跑构建，不跑真实路径。
4. 证据只留在聊天里。
5. 新增脚本不更新文档。
6. 新增文档不更新索引。
7. 密钥、日志、数据库、个人数据进入提交。
8. 外部工具权限过宽。
9. 高风险操作没有人工确认。
10. 没有回滚方案就做迁移或发布。

---

## 21. 与敏捷工作流的关系

敏捷工作流不是另一套相反系统，而是全量工作流的轻量切片。

全量闭环保留完整能力：

```text
设计 -> 规则 -> 执行 -> 验证 -> 证据 -> 安全 -> 回滚 -> 交接
```

敏捷工作流保留日常必需动作：

```text
读入口 -> 判等级 -> 小范围实现 -> targeted test -> 必要同步 -> 简短交接
```

当敏捷任务发现影响面变大，就升级到完整闭环。
