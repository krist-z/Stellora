# 通用工作流补充清单

本文档补充完整闭环和敏捷工作流中容易遗漏的内容。它适合在搭建个人或团队 AI 工作流时作为检查表使用。

---

## 1. 工作流成熟度路线

可以按 4 个阶段逐步建设。

### Stage 1：最小可用

适合个人小项目或试验项目。

- 有 Agent 入口文档。
- 有 README。
- 有基本测试或验证命令。
- 有 secret 和生成物边界。
- 有最终回复模板。

### Stage 2：可持续维护

适合长期个人项目或小团队项目。

- 有项目规则文档。
- 有 docs 索引。
- 有脚本入口。
- 有证据记录。
- 有风险清单。
- 有工作区和 Git 边界。

### Stage 3：完整闭环

适合复杂产品、跨模块系统、真实用户路径。

- 有任务等级和风险等级。
- 有真实路径验收。
- 有工作流同步检查。
- 有 secret scan。
- 有回滚方案。
- 有审计和交接模板。

### Stage 4：高可信交付

适合生产、发布、安全、合规、客户交付。

- 有发布 runbook。
- 有回滚演练。
- 有监控和发布后验证。
- 有权限复核。
- 有依赖和供应链检查。
- 有人工确认记录。
- 有合规审查或法律/安全审查流程。

## 2. 常见遗漏项

### 2.1 文档遗漏

- 新脚本没有写进 README 或文档索引。
- 新配置项没有说明默认值和安全含义。
- 新接口没有同步协议文档。
- 新验收结果只写在聊天里。
- 旧结论没有被新证据覆盖。
- 决策原因没有记录，后续只能猜。

### 2.2 验证遗漏

- 只跑构建，没有跑用户路径。
- 只跑单元测试，没有跑跨模块场景。
- 只在 happy path 验证，没有覆盖失败路径。
- 没有验证回滚。
- 没有验证配置模板。
- 没有验证文档链接、脚本入口或证据质量。

### 2.3 安全遗漏

- 密钥写进示例、日志或错误输出。
- 本地数据库或客户数据进入提交。
- AI 把真实路径、账号、服务器、token 写进通用文档。
- 外部工具权限过宽。
- 使用真实生产凭据做测试。
- 删除或迁移前没有备份。
- 发布或推送前没有人工确认。

### 2.4 协作遗漏

- 多个 AI 或多人同时改同一文件。
- 没有说明当前工作区已有无关改动。
- 没有交接下一步。
- 没有记录未验证项。
- 没有记录残余风险。

## 3. 安全增强清单

### 3.1 默认禁止自动执行

除非用户明确授权，AI 不应自动执行：

- 提交、推送、发布。
- 删除、批量移动、批量重命名。
- 数据库写入、迁移、清空。
- 修改权限、认证、访问控制。
- 调用外部系统写接口。
- 安装高权限工具、hook、后台服务。
- 复制或展示密钥。
- 处理未脱敏的敏感数据。

### 3.2 高风险任务必备

高风险任务必须具备：

```text
明确目标
影响范围
备份或快照
回滚方案
验证方案
人工确认
审计记录
残余风险
```

### 3.3 密钥泄露响应

如果发现密钥泄露：

1. 停止继续传播。
2. 不在聊天里重复展示密钥。
3. 记录泄露位置和影响范围，使用脱敏形式。
4. 轮换密钥。
5. 删除或重写暴露文件。
6. 检查日志、提交历史和外部存储。
7. 记录恢复结果。

## 4. 质量门禁

按项目类型选择。

### 4.1 代码项目

- 格式化。
- lint。
- 类型检查。
- 单元测试。
- 集成测试。
- 构建。
- 运行时 smoke test。
- secret scan。
- 依赖检查。

### 4.2 前端 / 桌面 / UI 项目

- 构建。
- 组件测试。
- 浏览器或窗口真实交互。
- 截图或视觉检查。
- 响应式检查。
- 可访问性检查。
- 文案溢出检查。
- 错误态和空状态检查。

### 4.3 数据项目

- 输入 schema 检查。
- 输出 schema 检查。
- dry-run。
- 样例数据验证。
- 差异报告。
- 备份。
- 回滚。
- 数据量和性能检查。
- 隐私和脱敏检查。

### 4.4 服务 / 运维项目

- 启动检查。
- 健康检查。
- 日志检查。
- 配置模板检查。
- 监控指标。
- 重启和回滚。
- 权限检查。
- 灾难恢复演练。

### 4.5 内容 / 研究项目

- 事实核对。
- 引用检查。
- 日期和时效性检查。
- 版权检查。
- 术语一致性。
- 目标读者检查。
- 人工审阅。

## 5. AI 使用风格适配

同一套工作流可以根据用户偏好调整。

### 5.1 简洁型

适合熟练用户。

- 少解释。
- 只给必要计划。
- 直接执行低风险任务。
- 收尾只列改动、验证、风险。

### 5.2 严格型

适合生产、高风险、团队项目。

- 每步先计划。
- 明确任务等级和风险等级。
- 所有副作用前确认。
- 强制证据和回滚。

### 5.3 教学型

适合学习者。

- 解释为什么这么做。
- 展示替代方案。
- 说明验证命令含义。
- 收尾总结学到的模式。

### 5.4 产品型

适合产品、设计和用户体验。

- 强调用户路径。
- 强调可用性、错误态、空状态。
- 强调文案和交互一致性。
- 验证真实体验，不只看代码。

### 5.5 研究型

适合资料、报告、方案。

- 强调来源。
- 强调时效性。
- 强调引用和反证。
- 明确推断和事实的区别。

## 6. 工具权限复核清单

定期检查：

```text
哪些工具仍在使用？
哪些工具有写权限？
哪些工具能访问外部系统？
哪些工具能读取敏感目录？
凭据是否过期或过宽？
是否有测试账号和生产账号混用？
是否记录了工具用途和 owner？
是否能撤销权限？
```

---

## 7. 多 AI / 多人协作清单

如果多人或多个 AI 同时工作：

- 每个任务有明确 owner。
- 写作用域不重叠。
- 共享当前状态和重要文件。
- 不回滚他人改动。
- 合并前运行统一验证。
- 冲突时先沟通，再修改。
- 最终证据只有一个最新结论。

多代理任务提示模板：

```text
Role:
Goal:
Read First:
Write Scope:
Do Not Touch:
Validation Needed:
Return:
```

## 8. 发布前检查

发布、交付或公开导出前：

```text
代码/内容验证通过
文档同步完成
证据记录更新
secret scan 通过
依赖风险可接受
生成物和本地数据未进入交付物
回滚方案明确
发布后检查明确
人工确认完成
```

## 10. 工作流健康仪表盘建议

成熟项目可以维护一个简单健康仪表盘。

建议指标：

- 最近一次测试时间和结果。
- 最近一次工作流同步检查。
- 未关闭高风险项数量。
- 最近证据是否过期。
- 文档链接是否有效。
- secret scan 是否通过。
- 依赖检查是否通过。
- 回滚 runbook 是否存在。
- 当前推荐下一步。

仪表盘可以是 Markdown、JSON、电子表格或项目管理看板，不要求复杂。
