## 4. 架构边界

按项目技术栈填写。例如：

- presentation / UI 层只负责展示和交互绑定。
- application / use-case 层负责状态编排和业务流程。
- domain 层负责稳定模型、业务概念和规则。
- infrastructure 层负责网络、数据库、文件系统、外部服务。
- controller / route 层只负责调度，不堆业务校验。
- schema / DTO 层负责入参校验和响应结构。

禁止：

- 在展示层解析复杂协议。
- 在 controller 中堆重复参数保护。
- 跨层直接依赖底层实现。
- 为赶进度绕过已有抽象。
- 在没有设计说明的情况下扩大模块职责。

## 10. 数据、隐私与 Secret 规则

数据分级：

| 等级 | 示例 | 处理规则 |
|---|---|---|
| Public | 公开文档、公开代码 | 可公开 |
| Internal | 内部设计、非敏感日志 | 不外发，写文档谨慎 |
| Confidential | 客户信息、业务数据、私有地址 | 最小化访问，不公开 |
| Secret | token、密码、私钥、session | 不展示、不提交、不长期保存 |
| Regulated | 医疗、金融、身份、未成年人等 | 需额外合规和人工确认 |

允许提交：

- 配置模板。
- 示例数据。
- 脱敏测试数据。

禁止提交：

- 真实 token、API key、密码、私钥。
- 真实用户、客户、财务、订单、身份信息。
- 本地数据库、日志、缓存。
- 登录状态、cookie、session。

提交、发布或公开导出前必须运行：

```text
<secret-scan-command>
```


文档落点：

记录：

```text
变更前状态:
备份位置:
回滚命令:
验证回滚成功的方法:
不可回滚部分:
人工确认:
```

涉及数据、生产、权限、发布、删除、迁移时，未准备回滚不得执行。

## 15. 工具与权限规则

- 外部工具默认只读。
- 文件工具只访问必要目录。
- 命令工具只运行必要命令。
- 数据库、项目管理系统、云平台、发布平台写操作必须明确授权。
- 工具凭据不写进文档。
- 工具权限定期复核。

## 16. Git / 发布规则

按实际项目替换：

- 只有用户明确要求提交才 commit。
- 提交前先运行 `<status-command>`。
- 只暂存本次任务相关文件。
- 不提交 secret、日志、数据库、构建产物、本机素材。
- 提交说明格式：`<rule>`。
- 推送规则：`<branch/remote rule>`。
- 发布规则：`<release rule>`。

发布前必须有：

- 验证通过。
- secret scan 通过。
- 回滚方案。
- 发布后检查。
- 人工确认。

## 17. Skill / Playbook 规则

- 全局 skill / playbook 保持通用，不写本项目私有路径、密钥或真实数据。
- 本项目专属工作流写入 Agent 入口文档、项目规则和 docs。
- 使用外部 skill 时，仍以本项目规则为准。
- 新增、删除或改造 skill 后，检查项目文档是否需要同步。

## 18. MCP / 工具服务器规则

- 工具服务器只作为工具接口。
- 工具配置不替代项目规则。
- secret 通过环境变量、密钥管理器或受控配置提供。
- 有写权限、外部系统权限或网络权限的工具要保守配置。
- 项目专属命令写在 scripts 和 Agent 入口文档，不写进工具配置。

## 19. 禁止事项

- 未验证就宣布任务完成。
- 构建通过就替代真实验收。
- 在代码或文档里写真实密钥。
- 提交日志、数据库、缓存、构建产物。
- 回滚用户或其他工具的无关改动。
- 新增脚本或文档后不更新索引。
- 让全局 skill 覆盖项目规则。
- 无备份迁移数据。
- 未确认就发布、删除、推送或改权限。

## 20. 例外处理

如果必须偏离本规则，必须说明：

1. 为什么现有规则无法满足需求。
2. 偏离范围。
3. 持续时间。
4. 风险和回滚计划。
5. 需要同步的文档。
6. 人工确认记录。
