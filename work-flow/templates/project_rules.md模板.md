## 1. 文档目的

本文件定义当前项目的工程规则，覆盖架构边界、编码规范、文档同步、脚本入口、验证要求、安全边界和交付规则。

## 4. 架构边界

按项目技术栈填写。例如：

- presentation / UI 层只负责展示和交互绑定。
- application / use-case 层负责状态编排和业务流程。
- domain 层负责稳定模型、业务概念和规则。
- infrastructure 层负责网络、数据库、文件系统、外部服务。
- controller / route 层只负责调度，不堆业务校验。
- schema / DTO 层负责入参校验和响应结构。

禁止：

- 在展示层解析复杂协议。
- 在 controller 中堆重复参数保护。
- 跨层直接依赖底层实现。
- 为赶进度绕过已有抽象。
- 在没有设计说明的情况下扩大模块职责。

## 10. 数据、隐私与 Secret 规则

数据分级：

| 等级 | 示例 | 处理规则 |
|---|---|---|
| Public | 公开文档、公开代码 | 可公开 |
| Internal | 内部设计、非敏感日志 | 不外发，写文档谨慎 |
| Confidential | 客户信息、业务数据、私有地址 | 最小化访问，不公开 |
| Secret | token、密码、私钥、session | 不展示、不提交、不长期保存 |
| Regulated | 医疗、金融、身份、未成年人等 | 需额外合规和人工确认 |

允许提交：

- 配置模板。
- 示例数据。
- 脱敏测试数据。

禁止提交：

- 真实 token、API key、密码、私钥。
- 真实用户、客户、财务、订单、身份信息。
- 本地数据库、日志、缓存。
- 登录状态、cookie、session。

提交、发布或公开导出前必须运行：


## 15. 工具与权限规则

- 外部工具默认只读。
- 文件工具只访问必要目录。
- 命令工具只运行必要命令。
- 数据库、项目管理系统、云平台、发布平台写操作必须明确授权。
- 浏览器、桌面控制、移动端模拟器、监控、CI/CD、部署、安全扫描和通信平台属于高影响工具，必须按任务等级和风险等级选择。
- 工具凭据不写进文档。
- 工具权限定期复核。

能力路由规则：

| 能力类别 | 默认等级 | 使用条件 | 证据要求 |
|---|---|---|---|
| 官方资料查询 | R0/R1 | 依赖、框架、SDK、CLI、云服务用法可能变化 | 说明来源、版本或查询日期 |
| 本机命令和脚本 | R1/R2 | 构建、测试、状态检查、生成临时产物 | 记录命令、工作目录和结果 |

## 16. Git 提交与发布规则

提交基本要求：

- 一次提交只做一件事。
- 代码提交前必须完成工作流闭环，至少通过相关自检和测试。
- 只暂存当前任务相关文件，不得夹带无关修改。
- 提交内容必须真实反映本次改动，并说明“改了什么”和“为什么改”。
- 不提交 secret、日志、数据库、缓存、构建产物或本机素材。
- 只有用户明确要求提交时才执行 commit。

提交信息格式：

```text
<type>(<scope>): <subject>
```

示例：

```text
feat(auth): 增加短信登录
fix(api): 修复用户列表分页错误
docs(readme): 补充本地启动说明
```

允许的 type：

- `feat`：新增功能。
- `fix`：修复缺陷。
- `docs`：文档修改。
- `refactor`：重构，不新增功能、不修复缺陷。
- `style`：格式调整，不影响逻辑。
- `test`：测试相关。
- `chore`：构建、脚本、依赖和杂项维护。
- `perf`：性能优化。
- `build`：构建系统或依赖打包调整。
- `ci`：CI/CD 配置调整。
- `revert`：回滚提交。

Subject 与 scope 规则：

- Subject 使用简短明确、以动词开头的描述，建议不超过 50 个字符。
- Subject 不加句号，不写长段落，中英文风格保持统一。
- Scope 使用能表达影响范围的小写名称，例如 `auth`、`api`、`ui`、`config`。
- 范围不明确时可以省略 scope，但不能随意编造。
- 禁止使用 `update`、`fix bug` 等模糊提交信息。

远程操作：

- 推送、创建 PR、合并和发布必须分别确认目标仓库与分支。
- 推送规则：`<branch/remote rule>`。
- 发布规则：`<release rule>`。

发布前必须有：

- 验证通过。
- secret scan 通过。
- 回滚方案。
- 发布后检查。
- 人工确认。

## 17. Skill / Playbook 规则

- 全局 skill / playbook 保持通用，不写本项目私有路径、密钥或真实数据。
- 本项目专属工作流写入 Agent 入口文档、项目规则和 docs。
- 使用外部 skill 时，仍以本项目规则为准。
- 新增、删除或改造 skill 后，检查项目文档是否需要同步。
- 当全局 skill、插件或 MCP 与本项目验证入口冲突时，以本项目验证入口为准；全局能力只能作为补充。
- 使用插件或 MCP 前，先确认市场是否已安装、插件是否启用、MCP 是否已登录且权限足够；token-backed MCP 还要确认目标空间、写入范围和密钥边界；未安装、未启用或未登录的能力不得写入完成证据。

## 18. MCP / 工具服务器规则

- 工具服务器只作为工具接口。
- 工具配置不替代项目规则。
- secret 通过环境变量、密钥管理器或受控配置提供。
- 有写权限、外部系统权限或网络权限的工具要保守配置。
- 项目专属命令写在 scripts 和 Agent 入口文档，不写进工具配置。
- 新增、停用或改变工具权限时，同步 MCP 配置说明、Agent 入口文档和相关证据。
- 市场未安装项、已安装未启用项、MCP 未登录项、token-backed MCP 的权限边界都要在能力复扫记录中明确标注。

## 19. 禁止事项

- 未验证就宣布任务完成。
- 构建通过就替代真实验收。
- 在代码或文档里写真实密钥。
- 提交日志、数据库、缓存、构建产物。
- 回滚用户或其他工具的无关改动。
- 新增脚本或文档后不更新索引。
- 让全局 skill 覆盖项目规则。
- 无备份迁移数据。
- 未确认就发布、删除、推送或改权限。

## 20. 例外处理

如果必须偏离本规则，必须说明：

1. 为什么现有规则无法满足需求。
2. 偏离范围。
3. 持续时间。
4. 风险和回滚计划。
5. 需要同步的文档。
6. 人工确认记录。
