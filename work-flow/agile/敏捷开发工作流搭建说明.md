# 敏捷开发 AI 工作流搭建说明

本文档是完整闭环工作流的轻量版，适合日常快速开发、bug 修复、小功能、局部脚本、局部文档和低风险配置调整。

敏捷工作流不绑定某个具体 AI 工具。任何 AI 助手只要能读取项目文件、理解规则、执行命令或辅助规划，都可以使用这套流程。如果 AI 支持计划模式，可以先让它根据本文件生成个人化版本。

---

## 1. 核心原则

敏捷不是跳过规则，而是只执行当前任务需要的规则。

日常任务保留 6 个动作：

```text
读入口 -> 判等级 -> 定边界 -> 小实现 -> 小验证 -> 小同步
```

对应到 AI 协作：

1. 先读项目 Agent 入口文档和必要规则。
2. 判断 L1 / L2，必要时升级 L3 / L4。
3. 只读当前任务相关文件。
4. 做最小 coherent change。
5. 跑能证明本次改动的最小验证。
6. 只同步本次结论需要的文档或证据。

---

## 2. 适合敏捷工作流的任务

适合：

- 小 bug 修复。
- 小功能。
- 单文件或少量文件调整。
- 文案、注释、配置模板。
- README、操作手册、局部文档修改。
- 新增一个小测试。
- 调整一个脚本参数。
- 按现有模式补一个类似入口。
- 只读分析和计划。

不适合，应该升级完整闭环：

- 跨模块或跨系统协议。
- 数据库 schema、迁移、批量数据处理。
- 持久化、权限、认证、支付、安全策略。
- 真实用户主流程或生产运行路径。
- 外部系统写入。
- 发布、删除、迁移、回滚。
- 处理敏感数据。
- 用户明确要求“完整闭环”“全流程”“同步证据”“发布”。

---

## 3. 敏捷任务等级

敏捷开发主要使用 L1 和 L2。

| 等级 | 适用任务 | 最低动作 |
|---|---|---|
| L1 Quick | 小文案、注释、低风险说明、轻微配置提示 | 读直接相关文件，改最小范围，静态/可读性检查或说明不适用 |
| L2 Standard | 普通 bug fix、小功能、局部测试、脚本调整 | 读项目入口和相关规则，改最小范围，跑 targeted test，同步必要文档 |

升级条件：

| 触发点 | 升级到 |
|---|---|
| 影响用户可见主流程 | L3 |
| 影响协议、数据库、持久化、权限 | L3 |
| 需要真实运行路径证明 | L3 |
| 涉及生产、发布、删除、迁移、安全、敏感数据 | L4 |
| 用户要求完整闭环 | L3 或 L4 |

---

## 4. 敏捷项目最小配置

一个项目想支持 AI 敏捷协作，至少需要：

```text
ProjectRoot/
├─ AGENTS.md 或 AI_GUIDE.md
├─ README.md
├─ scripts/
│  ├─ build 或 generate
│  ├─ test 或 validate
│  └─ start/status 可选
└─ docs/ 可选，但长期项目推荐保留
```

如果项目复杂，再补：

```text
project_rules.md
docs/文档索引.md
docs/任务结束闭环清单.md
docs/验证证据.md
docs/风险清单.md
```

最小要求是让 AI 明确知道：

- 怎么构建或生成。
- 怎么测试或验证。
- 哪些文件不能改。
- 哪些信息不能提交。
- 当前项目先读什么。

## 5. 敏捷版 Agent 入口文档

敏捷版入口文档可以很短，但必须包含：

```text
# Project AI Guide

## Priority
- 用户最新请求
- 本文件
- README / project_rules / docs
- 全局 skill 或通用 playbook

## Project Map
- 源码或主要产物目录
- 测试目录
- 脚本目录
- 文档目录
- 生成物目录

## Boundaries
- 不提交 secret
- 不提交日志、数据库、构建产物
- 不回滚无关改动
- 高风险操作先确认

## Task Levels
- L1 小改
- L2 标准
- 什么时候升级 L3/L4

## Verification
- 小改检查
- 代码/文档/数据/设计验证命令
- 工作流同步命令

## Closeout
- 改了什么
- 跑了什么
- 没跑什么以及原因
- 风险和下一步
```

敏捷入口文档的重点是让 AI 少问、快动手，同时不越界。

## 6. 敏捷提示词模板

推荐准备 6 个常用提示。

### 6.1 继续

```text
请按当前项目 Agent 入口文档继续，从项目文档和现有证据读取上下文，不要让我重复。任务：{{task}}
```

### 6.2 只读

```text
只做只读分析，不改文件，不运行有副作用命令。读取相关规则、文件、脚本和证据后，给出结论、风险和下一步。任务：{{task}}
```

### 6.3 计划

```text
先进入计划模式。请给出目标、影响范围、任务等级、风险等级、执行步骤、验证方式和需要我确认的事项。确认前不要改文件。任务：{{task}}
```

### 6.4 小改

```text
按 L1 Quick 执行。只读直接相关文件，做最小改动，运行静态/可读性检查或说明不适用。任务：{{task}}
```

### 6.5 标准开发

```text
按 L2 Standard 执行。读取相关规则，做最小实现，运行 targeted test，同步必要文档；如果影响面超过局部，请升级并说明原因。任务：{{task}}
```

### 6.6 文档同步

```text
按文档/工作流同步执行。只改必要规则、索引、清单或模板；完成后运行项目已有同步检查，说明未运行构建或真实验收的原因。任务：{{task}}
```

## 7. 敏捷执行清单

### 7.1 开始前 3 问

AI 开始前只需要判断：

1. 这是 L1 还是 L2？
2. 必须读哪些最少文件？
3. 什么验证能证明这次改动？

如果答案涉及生产、删除、迁移、权限或敏感数据，停止敏捷流程，升级完整闭环。

### 7.2 编辑前

执行：

```text
读 Agent 入口文档
读直接相关 project_rules / README / docs
用搜索工具找相关代码、文档或脚本
查看必要的工作区状态
```

不需要：

- 全量读所有文档。
- 运行所有验收脚本。
- 更新所有工作流文档。
- 做无关重构。

### 7.3 实现中

原则：

- 保持改动局部。
- 沿用项目现有风格。
- 新配置只写模板，不写真实值。
- 不引入新依赖，除非明确必要。
- 不访问外部系统，除非用户明确授权。
- 不做批量删除或迁移。
- 发现影响面扩大时，暂停并升级等级。

### 7.4 验证

选择最小验证。

通用验证类型：

```text
静态检查：格式、lint、类型检查、拼写、链接
单元测试：只跑相关测试或小范围测试
集成测试：跨模块行为
运行时验证：真实启动、真实 UI/API/数据流
文档验证：搜索旧术语、检查链接、检查索引
安全验证：secret scan、权限检查、依赖检查
```

示意命令：

```text
<test-command>
<lint-command>
<typecheck-command>
<build-command>
<validate-command>
<workflow-check-command>
<secret-scan-command>
```

不要把全项目所有专项验收作为 L2 默认动作。只有触碰真实运行时路径、数据、权限或外部系统时才升级。

### 7.5 收尾

最终回复最少包含：

```text
已改：<文件和目的>
验证：<命令和结果>
未验证：<原因>
风险/下一步：<如果有>
```

只读分析：

```text
只读完成：读取了 <文件>，没有改动文件。结论是 <...>。建议下一步 <...>。
```

## 8. 敏捷文档同步规则

不是每次都要更新所有文档。

### 8.1 必须同步的情况

| 改动 | 至少同步 |
|---|---|
| 新增或改了脚本入口 | README、环境说明或文档索引 |
| 改了协议、配置项或数据结构 | 配置说明、需求/设计文档 |
| 改了用户可见主流程 | 对应需求/设计和验收记录 |
| 改了验证脚本并得到新结论 | 验证证据文档 |
| 改了项目规则 | Agent 入口文档或项目规则相关入口 |
| 改了全局 skill / playbook / prompt | 相关说明或能力清单 |
| 涉及风险或回滚 | 风险清单或运行手册 |

### 8.2 可以不同步的情况

| 改动 | 说明 |
|---|---|
| 修局部 typo | 最终说明即可 |
| 只改内部注释 | 无长期规则变化可不改 docs |
| 小测试补充 | 不改变验收口径可不改总文档 |
| 局部风格修正 | 不改变规则可不改项目规则 |

## 9. 敏捷安全规则

即使是敏捷流程，也必须保留安全底线。

默认禁止 AI 自动执行：

- 删除大量文件。
- 覆盖数据库或持久化数据。
- 提交、推送、发布。
- 修改权限或认证策略。
- 访问外部系统写接口。
- 复制、展示或保存密钥。
- 安装高权限工具、hook 或后台服务。

敏捷任务的最小安全检查：

```text
是否涉及 secret？
是否涉及用户数据？
是否涉及外部系统？
是否可回滚？
是否需要人工确认？
是否会影响他人环境？
```

如果任一答案为“是”，考虑升级。

## 10. 敏捷 skill / playbook 使用

敏捷开发中使用 skill 的原则：

```text
只在它能明显减少重复探索时使用。
```

适合：

- 需要固定测试驱动流程。
- 需要浏览器或 UI 验收。
- 需要查询官方文档。
- 需要创建新 skill 或团队 playbook。
- 需要完整项目闭环。

不适合：

- 小文案硬套大型 skill。
- 项目入口文档已经写清，还让全局 skill 覆盖项目规则。
- 把 skill 当成万能脚本执行器，忽略项目验证入口。

创建条件：

- 同类任务重复 3 次以上。
- 每次都读同一批资料。
- 每次都跑同一组验证。
- 每次都需要同一模板。

## 11. 敏捷工具服务器使用

工具服务器可以是 MCP，也可以是 IDE 插件、CLI、浏览器自动化、数据库连接、文档库连接等。

敏捷使用原则：

- 能用项目脚本就用项目脚本。
- 查技术资料优先官方文档。
- 不用工具写入 secret。
- 不让工具配置替代项目规则。
- 小任务不调用一堆外部服务。
- 外部系统写操作需要授权。

工具权限快速检查：

```text
这个工具能读什么？
能写什么？
是否有外部副作用？
凭据来自哪里？
失败后怎么恢复？
是否有审计记录？
```

## 12. 按项目类型选择敏捷入口

### 12.1 服务型项目

优先读：

```text
Agent 入口文档
配置说明
运行手册
测试说明
部署或状态检查文档
```

常用验证：

```text
单元测试
导入或启动检查
健康检查
配置模板检查
secret scan
```

升级点：

- 真实部署。
- 生产配置。
- 外部 API。
- 用户数据。
- 权限和认证。

### 12.2 前端或桌面项目

优先读：

```text
Agent 入口文档
项目规则
设计或 UI 规范
组件或页面说明
测试入口
```

常用验证：

```text
构建
组件测试
截图或视觉检查
浏览器/窗口真实交互
可访问性检查
```

升级点：

- 用户主流程。
- 复杂状态。
- 视觉回归。
- 支付、权限、账户。

### 12.3 数据或脚本项目

优先读：

```text
Agent 入口文档
数据说明
输入输出 schema
脚本说明
风险清单
```

常用验证：

```text
样例数据测试
dry-run
输出 diff
数据校验
备份和回滚检查
```

升级点：

- 批量写入。
- 删除。
- 迁移。
- 真实业务数据。

### 12.4 内容或研究项目

优先读：

```text
目标说明
风格指南
引用规则
事实来源
交付格式
```

常用验证：

```text
事实核对
引用检查
格式检查
重复和矛盾检查
人工审阅
```

升级点：

- 医疗、法律、金融。
- 对外发布。
- 引用真实人物或公司。
- 涉及版权材料。

## 13. 敏捷任务示例

### 示例 1：文案 typo

```text
等级：L1
读：相关资源文件或 README
改：一处文案
验证：搜索旧词是否还存在
同步：无
```

### 示例 2：补一个单元测试

```text
等级：L2
读：Agent 入口文档、相关源码、相关测试
改：测试文件和必要源码
验证：相关测试或全量轻测试
同步：如果行为口径变化，更新 docs；否则最终说明即可
```

### 示例 3：修局部 UI 状态

```text
等级：L2，若影响真实用户主流程则升 L3
读：Agent 入口文档、项目规则、相关 UI 文件和设计说明
改：最小范围
验证：构建 + 相关测试 + 必要视觉检查
同步：如用户可见流程变化，更新设计或验收记录
```

### 示例 4：改配置加载逻辑

```text
等级：L2 或 L3
读：Agent 入口文档、配置说明、相关源码、测试说明
改：配置解析和测试
验证：配置模板测试 + 启动检查
同步：如果配置项变化，更新配置说明
升级：如果影响生产配置、密钥或部署，则 L4
```

## 14. 敏捷反漂移检查

每隔一段时间做一次轻量反漂移：

```text
1. Agent 入口文档里的验证命令还有效吗？
2. 新脚本是否出现在 README 或文档索引？
3. 新文档是否被索引引用？
4. 证据文档是否仍是最新结论？
5. 生成物和密钥是否被忽略？
6. 全局 skill 是否仍保持通用？
7. 工具服务器权限是否仍最小化？
8. 风险清单是否有未关闭的高风险项？
```

## 15. 敏捷最终回复模板

简短任务：

```text
已完成：修改了 <文件>，把 <旧行为> 调整为 <新行为>。
验证：运行 <命令>，结果 PASS。
```

标准任务：

```text
已完成：
- <文件 A>：<目的>
- <文件 B>：<目的>

验证：
- <命令>：PASS

未覆盖：
- <未跑项>，原因是 <原因>。

风险/下一步：
- <如果需要>
```

只读任务：

```text
只读分析完成，没有改文件。
结论：<结论>
依据：<关键路径>
建议下一步：<动作>
```

---

## 16. 一句话准则

```text
小任务不要大动干戈，大任务不要假装小。
```

只要 AI 能稳定做到“知道边界、做最小改动、跑最小证明、留下必要记录、遇到风险及时升级”，敏捷开发体验就会轻快又可靠。
